# 跨会话记忆关闭后仍注入：修复记录

## 原因与复现

实时设置中 crossSessionMemoryEnabled=false，保存状态正常。主插件 lib/index.mjs 与 QQ、Telegram 的运行时分别打包，原先的 provider / runtime 模块变量各有一份。通道包读不到主插件的配置，provider=null 会退回空配置，空配置又按默认开启处理，因此可能从默认记忆目录加载跨会话尾注。

新增回归测试分别用 esbuild 生成两个独立包：修改前在“通道应取得主插件 provider”的断言上失败；修复后通过。全部测试仅使用临时目录里的合成记忆，不读取或更改真实聊天记录。

## 修改

- 新增 cross-session-runtime-state.mjs，使用同进程的 Symbol.for 槽共享 provider 与运行时配置回调；主包和通道包读取同一份实时开关。
- 未安装 provider 或运行时配置不可用时，不注入、不写入，避免空配置默认开启。
- 直接调用 enrichInboundEvent 也遵守总开关。
- 已排队、已带记忆尾注的消息在开关关闭后进入桥接时，移除本插件的待注入字段，不修改用户正文或原始事件。
- 不更改用户设置、记忆文件、会话记录，不删除历史内容。

## 验证与生效

28 项跨会话记忆测试通过，包括跨打包共享状态、开启→关闭、停止写入、清除排队尾注、主开关覆盖席位开关和无配置时关闭。

主包、Telegram 和 QQ 运行时均需重新构建并重载。源代码修复不代表正在运行的宿主已使用新代码。本轮不自动重启 DSH。

已经在旧会话中注入的记忆可能仍保留在该会话历史或其压缩摘要里，关闭开关不能让模型自动忘记已读内容。修复阻止后续注入；要完全排除历史影响，可在加载修复后用新会话验证。没有自动清理或改写用户的历史。


## Telegram 专项检查（2026-11-24）

Telegram 安装与 QQ 相同的 person-memory 注入和回复写入钩子，上轮重新生成的 lib/channel-telegram.mjs 已包含共享实时开关状态和配置缺失时关闭的保护。当前宿主启动时间晚于这份修复产物；实时设置显示 Telegram 启用、跨会话记忆总开关关闭且已保存。

跨打包回归测试现分别覆盖 Telegram / QQ；Telegram 额外验证总开关开启时产生 person-memory，关闭后私聊和群聊均不注入，嵌套 enabled=false 同样生效，排队尾注被清除且关闭时不写记忆文件。共 51 项相关测试通过。未发送真实 Telegram 消息，未改动用户设置或聊天历史。
